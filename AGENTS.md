# Repository instructions

## Purpose and current state

- This repository is for ideating and building a Databricks App.
- The repository currently contains tooling and workflow guidance only. Do not choose or scaffold an application framework until the product, data-access, and persistence decisions are explicit.
- Keep credentials out of the repository. Never commit tokens, `.databrickscfg`, generated OAuth material, or real secret values.
- Repository-scoped official Databricks skills live under `.agents/skills`. Load the smallest relevant skill before Databricks-specific work.

## Databricks workflow

- Load `databricks-core` before using the Databricks CLI. List all available profiles with `databricks auth profiles`, show them to the user, and let the user choose. Never auto-select a profile, even when only one exists.
- Load `databricks-apps` before app scaffolding or implementation. Follow its data-access decision gate and state-storage guidance.
- For any data-displaying custom app, also load `databricks-app-design` before UI implementation.
- Prefer AppKit for a new full-stack custom app unless requirements justify another framework. Derive features and resource keys from `databricks apps manifest`; never guess them.
- Do not silently provision a Databricks App, SQL warehouse, Lakebase project, secret, catalog object, or other workspace resource. Obtain the user's explicit choice first.
- Before implementing data access, discover the actual tables and schemas with the relevant Databricks skill and CLI commands. Do not invent catalog, schema, table, resource, or environment-variable names.
- Use `app.yaml` and Declarative Automation Bundles as generated or documented by the selected template. Validate before deploying.

## Ideation and decisions

- Separate confirmed requirements, assumptions, options, and open questions.
- For a simple chart/KPI request, compare a managed AI/BI Dashboard with a custom Databricks App before choosing custom code.
- Capture a durable idea brief under `docs/ideas/` when the discussion produces a concrete product direction.
- Record accepted, consequential architecture or data decisions under `docs/decisions/` using the ADR template. Do not create an ADR for trivial implementation details.
- Keep the first implementation slice independently usable and testable; explicitly defer nonessential features.

## Development quality

- Inspect `git status` and existing files before editing. Preserve user-authored or unrelated changes.
- Follow the commands and package manager generated by the selected Databricks template. Do not replace or upgrade AppKit dependencies without an explicit requirement.
- Add or update focused tests with behavioral changes. Run the narrowest relevant checks while iterating, then run the template's full validation suite before declaring the scope complete.
- Treat lint, formatting, typecheck, tests, and `databricks apps validate` failures as real failures. Fix them or report the exact blocker.
- Keep deployable files under the Databricks Apps per-file size limit and exclude local environments, secrets, caches, test output, and agent assets from deployment.

## Small-scope commit discipline

- A small scope is one independently reviewable concern: one setup change, one decision document, one feature slice, one bug fix, or one focused refactor.
- Immediately after a small scope is implemented and its relevant checks pass, commit it. Do not wait to batch unrelated completed scopes into one commit.
- Before every commit, review `git status`, review the staged diff, and stage only files belonging to that scope.
- Never mix formatting-only changes, refactors, generated artifacts, dependency updates, and product behavior in one commit unless they are inseparable.
- Do not amend, rebase, force-push, or rewrite existing commits unless the user explicitly asks.
- If a commit cannot be created because checks, hooks, identity, or permissions fail, keep the changes intact and report the exact blocker.

## Conventional Commits

- Every commit subject must use `type(optional-scope): imperative description`.
- Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Use a short lowercase scope when it adds clarity, such as `app`, `auth`, `sql`, `lakebase`, `bundle`, `deps`, or `codex`.
- Use an imperative, concise subject without a trailing period.
- Mark breaking changes with `!` before the colon and explain them in the commit body.
- Examples: `feat(customer): add customer lookup`, `fix(auth): handle expired oauth session`, `docs(adr): choose analytics access`, `chore(codex): update databricks skills`.

## Repository commands

- Initial local setup: `./scripts/setup.ps1`
- Verify required tools and list profiles: `./scripts/verify-tools.ps1`
- Refresh official Databricks skills: `./scripts/update-databricks-skills.ps1`
- Once an app is scaffolded, document its exact local run, test, validate, and deploy commands in the root README and use those commands as the source of truth.

## Definition of done

- The requested behavior or artifact is complete for the agreed small scope.
- Relevant automated checks pass, or the exact unverified item and reason are reported.
- Documentation and decision records reflect any changed workflow or architecture.
- No credentials, local state, or unrelated user changes are staged.
- The completed small scope is committed with a valid Conventional Commit message.
